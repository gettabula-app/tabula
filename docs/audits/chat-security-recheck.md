# Chat security recheck (CDX-44)

Reviewed DevOps commit `46812cb85cfc4459f5aa964eb3ac0bd197c39f46` against `1e403fa` in read-only mode. No source files were changed.

## Account switching

The same-tab signed-in A → B path is handled synchronously: `dropPreviousUser` starts clearing the stored caches before `ME_KEY` changes, the chat auth listener resets memory and unread state and closes the socket, and the socket callback ignores frames from a socket that is no longer current (`src/auth.ts:146-148,239-244`; `src/chat.ts:177-178,748-792`). Sign-out also resets chat. Two remaining issues bypass that path:

- **P1 — A's cached chat can be shown to B after a reload or a sign-in in another tab.** `dropPreviousUser` compares only an already `signed-in` in-memory state (`src/auth.ts:146-148`); a new page starts `unknown` (`src/auth.ts:22`) and `initAuth` commits the returned user without comparing the previously cached `ME_KEY` (`src/auth.ts:168-173`). The chat auth listener is local to each tab and has no cross-tab identity notification (`src/chat.ts:782-793`). The shared IndexedDB database is not keyed by user (`src/chat-cache.ts:9-14,64-72`); `load` renders its saved messages before the server response (`src/chat.ts:324-328`), and a failed/denied request leaves those messages in the channel state (`src/chat.ts:353-366`). Thus a B tab can display A's saved text for a known channel, while an already-open A tab can retain A's socket and receive A frames after B becomes active elsewhere. **Fix:** synchronize identity changes across tabs, compare the cached identity on boot, and scope cached channels/outbox entries to the user.
- **P2 — An in-flight outbox read can restore and send A's draft after a same-tab reset.** `openChat` starts `ensureOutbox` (`src/chat.ts:542-550`); its pending `readOutbox` completion unconditionally merges saved entries into memory and calls `flush` (`src/chat.ts:432-439`). `resetChat` clears the current outbox and bumps `generation`, but cannot cancel that callback (`src/chat.ts:748-777`). A late callback can therefore load A's saved drafts after B is active and flush them using the current same-origin session (`src/chat.ts:451-464`; `src/api.ts:609-613`). **Fix:** capture the auth generation/user when loading the outbox and discard the result if either changed before it resolves.

## Purged history and live arrivals

The new `load` merge correctly empties stale saved messages on a successful empty page and retains message/edit frames observed during that fetch (`src/chat.ts:253-259,318-352`). The retention behavior does not cover reconnect catch-up, and three fetch races remain:

- **P2 — Reconnect catch-up can keep messages the server has purged.** `catchUp` merges fetched results into the old local list when the gap is closed, including when the server returns an empty list, then saves the merged list (`src/chat.ts:375-402`). If retention removed IDs that were already in the cache, they survive and are persisted again. **Fix:** reconcile the cached list against an authoritative retained-history snapshot during reconnect instead of only merging newer pages.
- **P2 — A delete arriving during `load` can be undone by the older page response.** Message/edit frames add IDs to `arrived`, but delete frames only apply a tombstone (`src/chat.ts:253-267`). When the earlier page resolves, `load` filters that tombstone out because its ID is absent from `arrived`, then merges the stale live copy from the page (`src/chat.ts:338-342`; tombstones otherwise win in `src/ui/chat-logic.ts:39-43`). **Fix:** preserve delete tombstones received during the fetch in the same reconciliation set as message/edit frames.
- **P2 — Overlapping newest-page loads can lose live messages.** `setVisible` can start another `load` after a hide/show cycle without checking `ch.loading` (`src/chat.ts:601-608`); each call replaces the shared `arrived` set (`src/chat.ts:318-322`). One response can consume and clear arrivals before the later response replaces the list, losing a socket message (`src/chat.ts:338-342`). **Fix:** serialize newest-page loads per channel or use per-request arrival sets and merge results by sequence.
- **P2 — A wide reconnect catch-up can discard frames received while it paginates.** `catchUp` does not set `ch.loading` or capture arrivals; when its page limit is exceeded it replaces `ch.messages` with `fetched` (`src/chat.ts:375-398`). A socket message merged while the pages were in flight can therefore be overwritten. **Fix:** record and merge socket arrivals across the entire catch-up operation before replacing the list.
